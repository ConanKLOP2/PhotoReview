# Whole-project code review and optimization candidates

**Date:** 2026-09-27. **Baseline:** `origin/master` `13e33df` (`v2.0.187`). **Status:** static review; no production changes. PR #183 is open and is outside this baseline.

## Method and coverage

Three read-only subagent passes covered App/WPF, Core/Imaging/TurboJPEG, and Windows/platform/build/tooling. The lead checked cross-project call paths and evidence for reported findings. Reviewed project references, architecture contracts, selected tests and the complete `src` file inventory (255 C# files). Detailed function tracing concentrated on navigation, compare, cache, decode, preload, file-system, instance forwarding and benchmark hot paths. The remaining settings/localization/diagnostics helpers, standalone windows, much of pointer/XAML input routing and several low-risk Core helpers were **not** manually audited function by function. A build and the standard filtered test suite verify integration, but cannot establish that every function is optimal or prove NAS/GUI performance.

The review did not use a new benchmark run or a real NAS fixture. A source-level blocking call is confirmed; its frequency and user-visible latency on a given machine are measurement questions. Do not label the proposals below as measured speedups.

## Cross-project linkage checked

`App` references Core, Imaging, TurboJPEG, Platform.Windows and Benchmarking; Benchmarking uses Core, Imaging, Platform.Windows and PerfAnalysis; Core consumes Localization.Generator as an analyzer. The production flow is `MainViewModel`/`FolderLoadCoordinator` -> `ImagePresenter` -> thumbnail/preview services -> RAM/disk/source-byte caches and WPF/WIC/TurboJPEG decoders, while `PreloadScheduler` shares the preview/cache path. File actions flow through Core journal and Windows Recycle Bin adapters. The single composition root in `AppHost` is also used by the benchmark CLI and integration tests. The architecture tests and solution build cover project-reference wiring; the standard test filter covers 5 test projects. These checks do not validate real desktop rendering, NAS contention, Native/Slow/Manual categories, or every XAML handler.

No blanket recommendation to raise the cache beyond its existing policy: `RamBudgetPolicy.MaxPhysicalMemoryShare` is 0.5 and the configured preview-cache target on a 32 GiB machine is 16 GiB when the optional source-byte cache is off (`src/PhotoReview.Imaging/Preload/RamBudgetPolicy.cs:22`; `src/PhotoReview.Imaging/Caching/PreviewImageService.cs:174`). Source-byte cache already has in-flight dedup, bounded LRU and invalidation generations. Readability reporting and journal durability are explicit contracts; I/O proposals must preserve them.
