# Q-R29 option C part 1 -- navigation stat off the UI thread (before/after, simulated slow link)

Decision and design: [decisions/Q-R29-C.md](../decisions/Q-R29-C.md). This file: method, numbers, caveats.

## Method

- **Builds.** "before" = master `68dae1f8`; "after" = this branch. Both measured with PR #202's slow-link seam
  (`SlowLinkFileSystem`, `--slow-link-latency-ms`) cherry-picked **locally only** (not part of this PR; #202 is still open)
  plus this PR's harness addition (below). No other difference.
- **Harness addition (in this PR, `tools/PhotoReview.Benchmark.Cli`).** `session.json` now has `keyDispatch` (wall time of the
  synchronous key handler, i.e. everything a navigation runs on the UI thread before its first await -- the UI-thread block
  per navigation) and `keyUiBusy` (total dispatcher-operation time from a settle key until it settled, via
  `Dispatcher.Hooks`, `UiBusyMeter`). Key-to-present = PerfAnalyze `finalVisualMs` (KeyInput -> final Presented).
- **Fixture.** F4 `C:\Xiuren\[[WALLPAPER]` used read-only in place (no copies, no hard links): 2,058 files, 18,883,457,837
  bytes before and after every run (checked). `--cache-dir` isolated and emptied per run; `--mode Preview`; 8 preload workers
  (whole-folder preload runs throughout, so almost every navigation is a RAM hit -- the case where a stat dominates).
- **Scenarios** (scratch copies, not committed): S2 = open, waitIdle <= 20 s, 40 x Right paced by settle (max 600 ms);
  S3 = open, waitIdle <= 20 s, 100 x Right every 33 ms (key-held burst).
- **Latency** injected per metadata call: 0 (plain production file system), 2, 10, 30 ms. `Thread.Sleep` granularity on this
  box made "2 ms" cost ~11-14 ms per stat (see `stat` column), so treat it as a ~12 ms link.
- **Two passes**, order reversed (p1 before->after, p2 after->before per cell), one run each.
- **Machine load (not idle):** 12 logical CPUs, other Claude sessions and a mutation-test agent building/testing
  concurrently. `\Processor(_Total)\% Processor Time` sampled around each p2 run: 41-98 %, mostly 55-90 %; p1 was 86-100 %
  (logged for the first cells only). Latency P95s swing with this load; the UI-thread numbers do not.

## Results -- UI thread (the point of the change)

`dispatch` = synchronous key-handler time, ms (P50 / P95); `busy` = UI-thread busy per settle key, ms (P50 / P95).

| Scenario | Latency | before dispatch p1 / p2 | after dispatch p1 / p2 | before busy (p1 ; p2) | after busy (p1 ; p2) |
|---|---:|---|---|---|---|
| S2 | 0 | 1.2/12.8 ; 1.2/4.3 | 0.4/1.4 ; 0.5/3.7 | 30/189 ; 27/48 | 25/50 ; 31/52 |
| S2 | 2 (~12 eff.) | 14.8/19.0 ; 14.7/26.6 | 0.4/1.1 ; 0.5/3.6 | 47/69 ; 51/103 | 19/34 ; 32/64 |
| S2 | 10 | 15.4/28.0 ; 15.7/26.9 | 0.4/1.6 ; 0.5/3.3 | 64/100 ; 67/87 | 24/61 ; 26/38 |
| S2 | 30 | 45.0/63.9 ; 37.5/50.7 | 0.4/1.1 ; 0.4/1.1 | 110/138 ; 106/134 | 19/40 ; 24/42 |
| S3 burst | 10 | 15.2/26.7 ; 14.7/27.3 | 0.3/1.1 ; 0.4/2.1 | - | - |
| S3 burst | 30 | 43.1/48.0 ; 43.8/50.1 | 0.3/0.6 ; 0.6/3.8 | - | - |

Before, the UI thread was blocked for one full link round trip on every key (plus the post-present refresh stat -- visible in
`busy`, roughly 2x the latency). After, the key handler returns in ~0.4 ms whatever the latency, and UI busy time per key no
longer grows with latency. In the S3 burst the harness sends keys from the UI thread, so the before build could not even
deliver them on time: the 100-key phase took 6.3/5.7 s (10 ms) and 9.6/9.9 s (30 ms) instead of ~3.3 s + overhead, vs
4.6/4.2 s and 4.6/4.9 s after -- i.e. before, a held key "keeps going" after release; after, the app keeps up with input.

## Results -- key-to-present (finalVisual, ms, P50 / P95)

| Scenario | Latency | before p1 ; p2 | after p1 ; p2 | stat round trip P50 before -> after (p1 ; p2) |
|---|---:|---|---|---|
| S2 | 0 | 6.6/47.5 ; 5.1/51.7 | 4.5/22.0 ; 4.7/59.9 | 0.16 -> 0.46 ; 0.25 -> 0.55 |
| S2 | 2 (~12 eff.) | 17.7/28.5 ; 20.8/529 | 15.2/32.8 ; 19.4/38.7 | 13.6 -> 11.9 ; 11.3 -> 11.0 |
| S2 | 10 | 20.8/33.7 ; 21.2/35.8 | 19.9/56.1 ; 19.6/34.8 | 14.4 -> 16.0 ; 14.2 -> 14.6 |
| S2 | 30 | 48.5/89.0 ; 45.7/569 | 42.1/57.0 ; 47.1/64.3 | 43.8 -> 38.4 ; 34.6 -> 43.4 |
| S3 burst | 10 | 18.5/30.5 ; 18.6/35.5 | 18.9/32.4 ; 19.9/33.9 | 14.2 -> 15.0 ; 13.2 -> 14.7 |
| S3 burst | 30 | 46.6/53.9 ; 47.6/57.3 | 46.4/60.4 ; 44.4/67.3 | 41.8 -> 42.9 ; 42.5 -> 35.9 |

Key-to-present is **unchanged within noise** at every latency: the stat is still on the critical path (by design -- nothing may
be shown before freshness is known), it just no longer freezes the window. The two before-P95 outliers (529/569 ms, p2) are
single stalls under load; after had none, but one pass each is not enough to claim a tail improvement. The worker hop costs
~0.3 ms at P50 on local disk (latency 0: stat P50 0.16-0.25 -> 0.46-0.55 ms; P95 up to 7-9 ms under 80-100 % CPU, when the
worker or Dispatcher waits for a core) -- inside the finalVisual noise here.

**Burst semantics.** At 30 ms/stat and a key every 33 ms, the after build presents only the navigations still current when
their stat returns (S3 lat30: 52 and 40 of 101 navigations "incomplete" = superseded, dropped by design; queued stats of
superseded navigations are skipped without touching the disk), and lands on the last key's image. Before, every navigation
completed only because input itself was throttled by the blocked UI thread. `ReviewMetrics.PresentedImages` is recorded after
the post-present refresh stat, so in bursts it now counts fewer presents than images actually shown (harness settle logic
unaffected: S2 paces keys well above the stat time).

## Tests / mutation checks

New: `ImagePresenterTests.StatOffUiThread.cs` (5, delayed-stat `IFileSystem` fake + per-test worker, gates only, no delays),
`NavigationStatWorkerTests.cs` (3), `ThumbnailCacheTests.GetAsyncWithKnownStat_KeysByThatVersion`. Mutations (each applied
alone, reverted after): M1 stat made synchronous -> killed (4 fail, 1 hangs-then-fails); M2 token re-check after the stat
removed -> killed; M3 R7-1 refresh disabled -> killed (new test + existing R7-1 test); M4 dequeue-time cancellation removed ->
killed; M5 Missing reported as Error -> killed; M6 thumbnail key ignores `knownStat` -> killed; M7 worker completes
continuations synchronously -> survived the presenter tests, killed by
`NavigationStatWorkerTests.RunAsync_ContinuationDoesNotRunOnTheWorkerThread` (added for it). New tests 3x in a row: stable.

## Caveats

- Simulated link only (no NAS here); SMB client caching/pipelining not modelled (see #202's fragment on its branch,
  perf fragment "2026-09-27 qr29-slow-link-sim"). `ThumbnailCache.BuildKey` and `GetOriginalDimensionsAsync(path)`
  used `FileInfo` directly, outside the simulated seam, so on a real NAS the **before** build blocked even longer than
  measured (up to two more round trips per cold navigation); the after build does neither.
- Bandwidth cap not measured (preload byte reads bypass `IFileSystem`; that is part 2, see the decision file).
- Heavily loaded shared box, one run per cell per pass: use the UI-thread columns for conclusions, the latency columns only
  as "no regression".
