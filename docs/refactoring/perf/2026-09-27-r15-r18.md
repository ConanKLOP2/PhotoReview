# R15/R16/R17/R18 UI-thread cost measurements (2026-09-27; F4 = `C:\Xiuren\[[WALLPAPER]`, 1996 JPEGs, 18 GB, local NVMe)

Full review write-up: WORK-FULL-CODE-REVIEW-2026-09-27.md (removed 2026-10-01; `git show 2f2bf342:docs/refactoring/WORK-FULL-CODE-REVIEW-2026-09-27.md`).
Scope: measure the four remaining conditional findings (R15-R18) before deciding whether to fix any of them, per this
project's "measure first, fix only if material" precedent ([R01-R02-R03-R13](../decisions/R01-R02-R03-R13.md),
[R04-R14](../decisions/R04-R14.md)). No harness scenario exercises these four call sites directly (hash/dedup,
preload-lifetime start, drag-drop, diagnostics snapshot), so each was isolated with a dedicated Stopwatch measurement
of the exact calls the source makes, run against real F4 files/synthetic data sized to the finding's own scale
question. Throwaway console harness (not committed; reproducible from the snippets below), Release build, net10.0.

| Finding | What was measured | Result (median / P95 / max) |
|---|---|---:|
| R15 `FileHashService.GetAsync` pre-await stat | `new FileInfo(path).Length` + `.LastWriteTimeUtc` (the exact fields `GetAsync` reads before its first await), 1996 real F4 files | 0.030 ms / 0.050 ms / 2.39 ms (single outlier; all other samples 0.02-0.06 ms) |
| R16 `ReviewCatalog.EntriesSnapshot()` | `List<T>.ToArray()` at N=2000 (current F4 size), N=10,000 and N=50,000 synthetic entries, 20 iterations each | N=2000: 0.011/0.020/0.111 ms; N=10,000: 0.052/0.103/1.73 ms; N=50,000: 0.24/0.71/2.78 ms |
| R17 `DragDropInputService.Parse` per-path `Exists` checks | `Directory.Exists` + `File.Exists` per candidate path (the two calls `Parse` makes per item), 1/10/50 real F4 files dropped together, 30 iterations each | N=1: 0.054/0.130/0.433 ms; N=10: 0.543/0.680/0.897 ms; N=50: 2.88/4.26/4.33 ms |
| R18 `ReviewMetrics.Snapshot` source-open sort | `ConcurrentDictionary<string,long>.ToArray().OrderByDescending(...).Take(10)` at the documented cap `MaxTrackedSourceOpenPaths = 4096`, 50 iterations | 0.276 ms / 3.93 ms / 11.3 ms |

**Context for each result:**

- **R15:** even smaller than R01-R13's already-negligible 0.1-0.3 ms band (this measures 2 field reads vs. R02's `new
  FileInfo` + 2 fields). Warm-cache median 0.03 ms is noise against any UI budget.
- **R16:** `EntriesSnapshot()` only runs once per new preload lifetime (`PreloadScheduler.KickAsync` reuses the running
  scheduler task when one is already in flight for the current lifetime; a fresh snapshot is taken only when the prior
  lifetime's `CancellationTokenSource` was already cancelled -- see `PreloadScheduler.cs` around the `_preloadCtsGate`
  block), not once per navigation. Even at 50,000 entries (25x the current F4 fixture and well past this app's
  practical folder sizes -- AGENTS.md targets loading full folders into a 16 GiB RAM budget, which caps realistic
  catalog sizes long before 50k), the copy costs under 3 ms worst-case and ~0.24 ms typical.
- **R17:** `Parse` runs once per drop gesture, not per navigation. A 50-path drop (an unusually large multi-select drag)
  costs single-digit milliseconds on local NVMe -- still two orders of magnitude under the ~100 ms perceptible-latency
  threshold. This does not measure NAS/UNC-path latency (`Directory.Exists`/`File.Exists` against a slow or
  disconnected network share can block far longer per call); that scenario is unmeasured here, same caveat as
  Q-R29's open NAS question, but no local fixture exists to reproduce it.
- **R18:** `Snapshot()` is called from `WpfDialogService`'s diagnostics dialog (user-triggered, on demand) and from
  `PreloadScheduler`'s perf-instrumentation path (gated behind the harness's `perf` flag, not the default production
  path) -- never from the per-navigation hot path. The observed P95/max spikes (3.9/11.3 ms) at the full 4096-entry
  cap are real but land on an already-infrequent, user-initiated or diagnostics-only call, not a per-frame cost.

**Decision (no code change for any of the four):** all four costs are either sub-millisecond in the steady state
(R15, R16 at realistic sizes) or reach a few milliseconds only in already-infrequent, non-hot-path calls (R17's rare
large multi-drop, R18's on-demand diagnostics snapshot at its documented cap). None approaches the ~100 ms
perceptible-UI-latency threshold this project uses (see R01-R13's disposition), and none sits on a per-navigation
hot path the way R01/R02/R03/R13 do. Per AGENTS.md's "measure first, fix only if material" instruction and the
Mandatory Process (minimize I/O / maximize RAM / prioritize review speed), moving any of these four off the UI
thread would add `Task.Run`/async plumbing and a snapshot-freshness or cancellation contract to preserve, against
costs this measurement cannot show are real. This narrows R16 and R18's "conditional on catalog scale" and
"conditional on diagnostics cost" qualifiers with concrete numbers (50,000-entry catalog and 4096-entry diagnostics
cap both measured, both negligible); R17's NAS-latency case remains as unmeasured as Q-R29's, for the same
lack-of-fixture reason. No test was added and no source path changed for R15/R16/R17/R18.
