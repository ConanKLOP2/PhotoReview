# P02 — Recovery retry guarded against a concurrent retry in another process

**Decided 2026-09-27 (user):** add an R09-style guard to Recovery retry. Finding from the post-ledger review
(PR #201; report removed 2026-10-01, see `git show 2f2bf342:docs/refactoring/decisions/POST-LEDGER-REVIEW.md`).

## Problem

`RecoveryRetryService.RetryMoveOrCopyAsync`/`ExecuteRetry` re-validated only the filesystem (source present, size/mtime
unchanged, destination absent) and then began a new journal transaction unconditionally. `operations.jsonl` is shared by
every process on `InstanceMode.PerFolder`, and the Q-R27 live marker is not mutually exclusive. Two windows retrying the
same Failed entry could both pass the pre-checks; the winner moved the file and appended Committed, the loser's Move threw
(source gone) and `tx.Fail` appended a Failed record **after** the winner's Committed. Latest-entry resolution then showed
a completed Move as Failed, durably.

## Fix

Same read-latest/compare/act-only-if-still-current discipline as `OperationJournal.Dismiss` (R09) and
`AppendIfStillPending` (FA-01):

- `OperationJournal.AppendIfUnchangedSince(anchor, ownSince, entry)` (internal): under the journal lock, reads the Id's
  history and appends only if `anchor` (the retried Failed snapshot) is followed by exactly `ownSince` and nothing else.
  An anchor not present in the journal (caller-built snapshot) means the whole history must equal `ownSince`.
- `JournalTransaction(..., retryOf: failed)` replaces the `failWithoutPrepared` flag (only retry used it):
  - `TryBegin()` appends Prepared only if the snapshot is still the latest entry; otherwise nothing is appended, the
    marker is released and `Superseded` is set.
  - `Fail()` appends Failed only if the entries after the snapshot are exactly this transaction's own Prepared (or none,
    when the Prepared append itself failed). Checking the whole tail, not just the latest entry, also covers the
    interleaving where the loser's Prepared lands after the winner's Committed.
  - `Commit()` stays unconditional: the mutation was verified, so Committed is true.
- `RecoveryRetryService.ExecuteRetry` first skips the retry when the Id is live elsewhere (`LiveOperations.IsLive`, Q-R27).
  Any of the three guards returns `RecoveryRetryResult(Superseded: true)` with message `core.recovery.alreadyHandled`; no
  file is touched and nothing is journaled.
- `RecoveryWindow.ExecuteRetryAsync` drops the stale row on `Superseded` (like a skipped Dismiss) and `Retry_Click`
  shows an info dialog titled `recovery.retry.stale.title`. New keys appended at the end of `en.json`, `vi.json`,
  `en.notes.json`.

Residual (documented, not a data risk): in the cross-process interleaving where the loser's Prepared lands after the
winner's Committed, the loser's Failed is suppressed and its Prepared is the latest entry. The next startup reconcile
(`ReconcilePendingOperations`, marker gone) judges it from the filesystem and appends Committed (source gone, destination
matches); until then Recovery lists it as pending with verdict AlreadyDone. Across processes the check-then-append window is
still a single read, as for FA-01/R09; a true exclusive lock was not chosen (journal-format/locking change).

## Tests (Core with fakes; UI in Integration)

`tests/PhotoReview.Core.Tests/FileActions/RecoveryRetryRaceTests.cs` — two `OperationJournal` instances (separate locks and
live registries = two processes) over one `InMemoryFileSystem`, interleaved from file-system hooks:

- loser's Prepared lands after the winner's Committed → no Failed after Committed, loser `Superseded`, reconcile heals;
- second retry starts after the first's Prepared → refused, first commits;
- stale snapshot (newer Committed/Failed/Dismissed) → refused, no mutation, no append;
- Id live in another process → refused; after the marker is released the retry runs;
- genuine failure of a current snapshot still journals Failed.

`RecoveryWindowTests.Retry_SupersededByAnotherWindow_DropsTheStaleRow` / `Retry_NotSuperseded_KeepsTheRow`.

Mutation checks (each killed): Prepared appended unconditionally (4 tests fail); Failed appended unconditionally (the
loser-overwrites-winner test fails — pre-fix behaviour); Failed guarded by latest-entry-only (same test fails); `IsLive`
check removed; `Superseded` after Fail ignored; `TryBegin` result ignored; window keeps the stale row.
