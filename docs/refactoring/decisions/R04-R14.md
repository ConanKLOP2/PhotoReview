# R04/Q-R29 (local-disk evidence) / R14 — preload contention and startup sweep

Full code review (2026-09-27), from #195 (`perf/preload-contention-startup-sweep`):

**R04 / Q-R29** — Local-disk evidence: no software synchronization gap found between preload workers and the viewer decode (dedicated above-normal-priority thread + its own semaphore, per-key `SourceBytesCache` dedup with no lock held during reads, no shared decoder instance). Local F4 measurement (8 vs 0 preload workers, interleaved) showed the observed P95 tail tracked external CPU contention on the shared dev box, not the preload setting; preload OFF was never faster and was much slower cold (297 ms vs 19 ms P50). Narrows Q-R29 to a pure bandwidth-on-a-slow-link question -- still needs a real NAS/slow-link measurement. See [perf measurement](../perf/2026-09-27-r04-preload-contention-r14-startup-sweep.md).

**R14** — Fixed: `SessionStore`'s startup `SweepStaleTempFiles` sweep was measured at ~0.25-0.3 ms/stale file (100 files ~24 ms, 3000 ~700 ms-1.3 s real disk) -- material against the ~1.8 s startup budget, so it now runs on a background `Task` instead of blocking the UI-thread constructor; proven safe (Load/Save never touch `*.tmp`, and the existing 1-day age guard prevents the background sweep from ever racing a concurrent Save's own temp file). Construction is now 0.0-0.2 ms regardless of stale-file count.
