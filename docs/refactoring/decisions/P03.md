# P03: Undo limited to the current session

Decided by the user, 2026-09-27. Source: finding P03 in
`POST-LEDGER-REVIEW.md` (PR #201; removed 2026-10-01, `git show 2f2bf342:docs/refactoring/decisions/POST-LEDGER-REVIEW.md`).

## Problem

At startup, `JournalStartupRecovery.RunAsync` called `UndoService.ReadStartupHistory()`
(a bounded read of `OperationJournal.ReadCommittedMoves`, oldest-first, deduplicated
per destination) and then `UndoService.SeedHistory(...)`, pushing the recent
committed Moves from the *global* journal - every folder, every past run - onto
the in-memory Undo stack before the user did anything in this session.

Consequence: after restarting the app, or opening another folder from a second
window in `InstanceMode.PerFolder`, Ctrl+Z could undo a Move the user made in a
*previous* run, or in a *different* folder/window, not anything done in the
current session. That is surprising and, for PerFolder, could move a file the
current window's user never touched.

## Decision

Undo is limited to the current session. `JournalStartupRecovery.RunAsync` no
longer seeds `UndoService` from journal history at all; it now only reconciles
pending/interrupted operations (INV-6) and returns the entries it had to mark
Failed. The Recovery window, live-operation registry check (Q-R27) and pending
reconciliation are unchanged.

`RunAsync`'s signature dropped the `UndoService` and `IUiScheduler` parameters -
both were only there to seed the Undo stack on the UI thread, and are unused
without that step. `App.xaml.cs` (`RecoverJournalAsync`) was updated to match.

## Dead code removed

- `UndoService.LoadFromJournal()`, `UndoService.ReadStartupHistory()`,
  `UndoService.SeedHistory(...)` - deleted. Nothing else in `src/` called them
  (grepped); the only remaining callers were tests, updated/removed alongside
  (see Tests below).
- `OperationJournal.ReadCommittedMoves` / `ReadCommittedMovesReverse` /
  `StartupCommittedMoveLimit` were **kept** - `UndoService.UndoMoveAsync`'s
  compatibility fallback (fingerprint lookup for a Move added to the public
  history stack directly, not via `Register`) still calls
  `_journal.ReadCommittedMoves()`, and multiple `OperationJournalTests` /
  `JournalModelTests` / durability and concurrency tests assert on it directly
  as a property of the journal itself, independent of Undo seeding.

## Perf note

Removing the seed step means startup no longer does the bounded tail read of
the journal (up to 200 entries, or the reverse-tail scan for journals over
1 MiB) that `ReadStartupHistory` performed on the thread pool. `RunAsync` now
does strictly less disk I/O at startup than before - a plus per AGENTS.md's
"minimize disk reads" priority - with no behavior change to pending-operation
reconciliation, which still does its own full scan.

## User-facing strings

Grepped `core.undo.*`, `main.menu.undo*`, `settings.shortcut.undo`,
`status.*Undo*` and README in both `en.json`/`vi.json`: none promise "undo
survives a restart" or similar, so no localized string needed to change.

## Tests

- `JournalStartupRecoveryTests.cs`: updated every `RunAsync(...)` call site to
  the new 2-parameter signature; removed `ThrowingUiScheduler` and
  `RunAsync_SeedThrows_StillReturnsFailed` (tested the now-removed UI-dispatch
  step); removed `SeedHistory_KeepsSessionMovesOnTop` and
  `SeedHistory_SkipsMoveAlreadyRegisteredInSession` (tested a removed method).
  Renamed `RunAsync_CompletedPendingMove_CommittedAndUndoable` to
  `RunAsync_CompletedPendingMove_CommittedButNotUndoable` (now asserts
  `_undo.CanUndoMove` is **false**). Added
  `RunAsync_JournalHasCommittedMoves_UndoStackEmptyUntilSessionRegistersAMove`:
  mutation-check - a journal with a Committed Move from "a previous run" leaves
  a freshly constructed `UndoService` with an empty stack after `RunAsync`, and
  a Move registered afterwards (in-session) is still undoable. Re-adding a
  seeding call inside `RunAsync` would fail this test.
- `UndoServiceTests.cs`: replaced `_service.LoadFromJournal()` call sites with
  `_service.Register(...)` (the in-session path that now is the only way to
  populate Undo history). Replaced `LoadFromJournal_AfterUndo_DoesNotOfferReverseMove`
  with `Restart_AfterUndo_HasNothingToUndo`, asserting a freshly constructed
  `UndoService` over the same journal has nothing to undo.
- `FileActionSafetyEdgeTests.cs`: removed `ReadStartupHistory_MoveUndoMoveAgain_ListsTheFileOnce`,
  `ReadStartupHistory_DistinctFiles_KeepOrder` and
  `ReadStartupHistory_LargeJournal_MoveUndoMoveAgain_KeepsNewest` (tested the
  removed method's dedup/ordering logic, which no longer has any caller).
- `CrashMatrixTests.cs`: `UndoCrashedBeforeEachCall_RestartIsConsistent` used
  `UndoService.ReadStartupHistory()` only as a convenient journal-consistency
  check (not to test Undo seeding). Replaced with a local
  `ConsistentCommittedMoves` helper that inlines the same filter directly over
  `OperationJournal.ReadCommittedMoves()`, preserving the invariant check
  without depending on the removed method.
