# R09/R10 — recovery-dismiss race and stale glide-stop flag

Full code review (2026-09-27, `codex/full-code-review-20260927`) findings, fixed in #192:

**R09** — `OperationJournal.Dismiss` now re-reads the current latest entry per Id (reusing `ComputeLatestEntries`, same read-latest/compare/act-only-if-still-current pattern as `AppendIfStillPending`) and only appends a Dismissed record when it still matches the caller's snapshot; it returns a new `DismissOutcome(Dismissed, Skipped)` instead of a bare list so a stale Dismiss (raced by a concurrent retry/other process on `InstanceMode.PerFolder`) is reported back instead of silently overwriting the newer entry — `RecoveryWindow` now tells the user "N entries were already resolved elsewhere" and drops those rows instead of assuming they were cleared.

**R10** — traced as a non-issue: `PointerInputController._pressStoppedGlide` is set by `OnWindowPreviewMouseDown` (subscribed on the Window, the root of the image's own visual tree) and read/cleared by `OnImagePress`; WPF tunnels every single physical press through the Window before it can reach the image, so a later, unrelated press that reaches `OnImagePress` always re-triggers `OnWindowPreviewMouseDown` for itself first, overwriting any stale value with that press's own `StopKinetic()` result — no code path lets a stale flag leak into a later click. No source change; a regression test (`GlideStoppedByAnUnrelatedPress_ThenASeparateImageClick_StillTriggersClickToZoom`) pins the current (correct) behavior.
