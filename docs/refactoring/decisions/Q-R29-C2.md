# Q-R29 option C-2 -- preload read-throttle seam: built, measured, fixed

**Context:** [Q-R29-C.md](Q-R29-C.md) part 2 was a proposal only: #202's `SlowLinkFileSystem`/bandwidth limiter never
reached the real image-byte read path, because `SourceBytesCache`, `WicDirectDecoder`, `WpfBitmapImageDecoder`, and
`PreviewImageService` all opened files via their own direct `FileStream`, bypassing `IFileSystem.OpenReadShared`
entirely. This closes that gap: a real seam, a harness decorator wired onto it, an actual measurement on a
simulated slow link, and a fix informed by what the measurement showed.

## 1. The seam

`PhotoReview.Core.Abstractions.ISourceReader` (`src/PhotoReview.Core/Abstractions/ISourceReader.cs`):
`Stream OpenSource(string path, SourceReadPriority priority, int bufferSize = 1 MiB)`, `SourceReadPriority` =
`Viewer | Preload | Background`. Default implementation `PhysicalSourceReader` is byte-for-byte the
`FileStream(path, Open, Read, ReadWrite|Delete, bufferSize, SequentialScan)` every call site already used.

Every source-image byte open now goes through it: `SourceBytesCache.ReadAndCache`, `WicDirectDecoder.Decode`/`ReadInfo`,
`WpfBitmapImageDecoder.DecodeSource`/`ReadInfo` (via a new optional `ISourceReader` constructor parameter, default
`PhysicalSourceReader.Instance` so every existing direct-construction call site, including tests and
`ThumbnailCache`'s static `WpfBitmapImageDecoder.DecodeWithFallback` call, is unaffected), and
`PreviewImageService.DecodeFromSource`'s `PHOTOREVIEW_DIAG_PREREAD` pre-read. `DecodeRequest` gained a `Priority`
field (default `Viewer`); `PreviewImageService` threads the real lane through: `DecodeForViewerAsync` (the photo on
screen) tags `Viewer`, `DecodeAndCacheAsync` (preload/compare) tags `Preload`, the zoom viewer's own
`DecodeOriginalAsync` keeps the `Viewer` default. `SourceBytesCache.GetOrRead(path, priority)` carries it into the
byte-cache read too (dedup/generation/eviction contracts unchanged -- priority is metadata only, never part of the
cache key).

DI (`App.xaml.cs`): `services.AddSingleton<ISourceReader>(_ => PhysicalSourceReader.Instance)`, threaded into
`DecoderProviders.Create(ISourceReader)`, `SourceBytesCache`'s registration and `PreviewImageService`'s. Production
default is the pure pass-through -- **this is a pure refactor with identical default behavior**, confirmed by the
full existing test suite passing unchanged (`dotnet test`, `Category!=Manual&Native&Slow`: 4,509 tests, 0 failures,
before and after) with no new production behavior until the fix in section 3.

## 2. Measurement

**Harness:** `PhotoReview.Benchmarking.SlowLinkSourceReader` (new) wraps `ISourceReader` with the same
`SharedBandwidthLimiter` token bucket #202's `SlowLinkFileSystem` already used for `IFileSystem.OpenReadShared`, but
wired onto the seam decode/`SourceBytesCache` actually calls. `--perf-session --slow-link-bandwidth-mbps` now also
overrides `ISourceReader` (`tools/PhotoReview.Benchmark.Cli/PerfSession.cs`), so the same `SharedBandwidthLimiter`
instance throttles the foreground viewer read and every preload worker for real -- unlike #202, this reaches
production's actual read path (confirmed: `WicDirect` was the active backend, `UseSourceBytesCache=false` in every
run below, so every read went through the decoder's own `_sourceReader.OpenSource` call).

**Fixture:** two, to separate two different effects (see caveat below) -- F4 (`C:\Xiuren\[[WALLPAPER]`, read-only,
2,058 files, 18,883,457,837 bytes, checked unchanged before/after) and a 500-file/2,505,160,751-byte subset
(`fixture500`, hard-linked from F4, same 2-8 MB selection method as #202's own fixture) chosen so its 2.5 GB total
fits comfortably inside the default 16 GiB preview RAM cache (F4's 17.6 GiB does not).

**Scenario:** `tools/diag/scenarios/s4-jump.json` (40x Right + 20x Left + Home, event-driven settle: waits for
present + preload-idle, capped at 1500 ms) and `s3-next-burst.json` (200x Right @33 ms). `--mode Preview`,
`--cache-dir` isolated per cell, one run per cell (time budget; see caveats).

**Cells (10 ms latency, 20 MB/s bandwidth cap unless noted):**

| Fixture | Scenario | Preload | keySettle P50 / P95 | Timeouts/60 | Notes |
|---|---|---:|---:|---:|---|
| F4 | s4-jump | default (8) | 1511.4 / 1517.0 ms | 60/60 | confounded, see caveat |
| F4 | s4-jump | 0 (off) | 893.2 / 1051.3 ms | 0/60 | confounded, see caveat |
| F4 | s4-jump | default (8), **no simulated link** | 1510.4 / 1519.9 ms | 60/60 | baseline -- same numbers as the throttled row above |
| fixture500 | s4-jump | default (8) | (capped) >=1500 ms | 60/60 | step 2 `waitIdle` itself timed out at 60 s: 500 files x ~5 MB / 20 MB/s = ~125 s minimum to preload the whole folder at this cap, so preload never reports idle inside the harness's windows |
| fixture500 (500 files) | s3-next-burst | default (8) | n/a (no settle instrumentation) | idle after burst: TIMEOUT at 60s ("preload still busy") | |
| F4 | s3-next-burst | 0 (off), same link | n/a | idle after burst: 1568 ms ("preload done") | |

**First finding (confound, caught and controlled for):** F4 (17.6 GiB) exceeds the default 16 GiB preview cache, so
whole-folder preload keeps evicting/re-reading and *never* reports idle regardless of any simulated link -- the
**identical** ~1510 ms/60-timeout signature shows up with and without the slow-link override on F4. This is not
noise or contention; it is `PreloadController.IsIdle` genuinely never becoming true for this fixture/cache-size
pair, and it made the first pass of this measurement look like a null result. Switching to `fixture500` (fits the
cache) removed that confound, but reintroduced a different one: at 20 MB/s a 2.5 GB folder takes ~125 s to preload,
so even fixture500's `waitIdle` times out within the harness's windows purely from arithmetic (2.5 GB / 20 MB/s),
regardless of any contention with the viewer.

**Deterministic arithmetic (robust to both confounds and to this shared box's own load, ~58% CPU from concurrent
sessions during this run):** the F4 preload-off vs preload-on `s3-next-burst` comparison isolates the effect
cleanly because it does not depend on `IsIdle` at all: with preload **off**, the burst's post-burst `waitIdle` step
returned in 1.57 s ("preload done" -- there is nothing to wait for). With preload **on**, the identical `waitIdle`
step hit its 60 s timeout still reporting "preload still busy". Both runs use the exact same simulated link
(10 ms/20 MB/s) and the exact same burst; the only variable is whether preload is competing for the shared 20 MB/s
budget. N-way arithmetic explains why: a 20 MB/s link split across the viewer plus `_viewerBusyWorkerLimit`
(`Math.Max(2, ProcessorCount/3)` = 4 on this 12-core box) concurrent preload readers gives each ~4-5 MB/s: a 5 MB
image then takes ~1-1.25 s just to read, and that is *before* any of it is de-prioritized behind an already
in-flight preload read of a similar size -- consistent with the fixture500 `s4-jump` cell's keySettle P50 landing
almost exactly on the harness's own 1500 ms settle cap.

## 3. Decision: contention is material on a bandwidth-capped link -- fixed

Unlike R04 (local disk, no software sync gap, no fix) and unlike #202's own `lat10-bw20` comparison (which showed
preload ON far *faster* than OFF, but only because the bandwidth cap never reached decode then), this measurement
shows the opposite once the seam actually throttles the real read path: **preload competing for a capped link can
make the whole-folder preload never finish inside a normal review session**, not just add a fixed millisecond cost
per navigation. This is qualitatively different from every prior Q-R29/R04 local-disk finding and crosses the bar
for a fix.

**Fix (`PreloadScheduler.cs`):** the existing viewer-priority cap (`_target.ActiveViewerDecodes > 0` reduces
concurrent preload starts to `_viewerBusyWorkerLimit`, already in place before this change, R04 found it sufficient
on local disk) now drops further, to `SlowLinkViewerBusyWorkerLimit` (1), when the link looks slow --
`ReviewMetrics.DecodeMillisecondsEwma` (the same EWMA `PreloadScheduler` already reads for burst pacing) exceeding
`SlowLinkDecodeMsThreshold` (200 ms; local disk measures 15-50 ms P50 per R01-R04, a capped link measured 1000+ ms
per read above). Not 0: `running.Count < limit` must stay reachable from `running.Count == 0` or the scheduler's own
"nothing running, nothing more to queue" exit condition treats the pass as fully done and the task exits -- with a
hard 0 and no further navigation to wake it, preload would never resume filling the rest of the folder once the
viewer's own decode ends. A decode already in flight is still left alone (unchanged, as before) -- this narrows how
many *new* preload reads can start alongside the viewer's, it does not interrupt one already reading.

This is adaptive (no link-speed setting to add or get wrong) and provably inert on local disk: `DecodeMillisecondsEwma`
never crosses 200 ms there (R01-R04's own 15-50 ms figures), so every existing local-disk-measured behavior
(R04, "bursts use every worker") is unchanged -- confirmed by the full test suite passing unmodified.

**What this fix does NOT do:** it does not make the viewer's read strictly win against an *already in-flight*
preload read (the original proposal's token-bucket idea, "Viewer reads never wait"); it only stops *new* preload
reads from piling on. A full priority-aware bandwidth allocator remains a distinctly larger, separately-scoped
follow-up if a real NAS/wifi measurement later shows this partial mitigation insufficient -- deliberately not built
now, per the project's anti-speculative-complexity stance and this session's own time budget.

**Test (mutation-checked):** `tests/PhotoReview.Imaging.Tests/PreloadSlowLinkViewerPriorityTests.cs` -- (1) with
`DecodeMillisecondsEwma` pushed past the threshold and a viewer decode in flight, at most 1 concurrent preload
decode starts (structural, not timing-based: the scheduler cannot admit a second while `running.Count == limit`);
(2) with no samples (fast link), at least 2 concurrent preload decodes still start, proving the fix does not touch
the already-validated fast-disk path. Mutation (reverting the slow-link branch to always use
`Math.Min(workers, _viewerBusyWorkerLimit)`) killed: test (1) failed, observing 4 concurrent decodes instead of
&lt;=1.

## Caveats

- Same shared, heavily-loaded box every prior Q-R29 fragment flags (~58% CPU from concurrent sessions during this
  run) -- the deterministic arithmetic (bytes moved / configured cap, and the binary "did `waitIdle` finish or hit
  its cap" signal) is used for the conclusion instead of raw wall-clock P50/P95, which this box's load makes
  unreliable on its own (see the F4 confound above, where identical numbers appeared with and without any simulated
  link at all).
- No real NAS: this is still a simulated link (Thread.Sleep-based token bucket), not real SMB/wifi protocol
  behavior (oplocks, pipelining, small-file overhead) -- same caveat every Q-R29 fragment before this one carries.
- The fix is deliberately partial (see "What this fix does NOT do" above); it is evidence-based for the scenario
  measured (whole-folder preload vs. one viewer read sharing a capped link), not a general bandwidth-fairness
  guarantee.
