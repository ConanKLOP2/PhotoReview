# R15/R16/R17/R18 — remaining UI-thread cost findings from the whole-project review

Full-code-review findings (`WORK-FULL-CODE-REVIEW-2026-09-27.md`) about conditional UI-thread costs in the hash
service, catalog snapshot, drag-drop parsing and diagnostics metrics: measured on F4 (`C:\Xiuren\[[WALLPAPER]`,
1996 JPEGs, 18 GB, local NVMe, no NAS fixture available) and, for the two scale-dependent findings, at synthetic
sizes well past current real-world use. All four measured negligible against this project's ~100 ms
perceptible-latency threshold; no fix applied to any of the four (see
[perf measurement](../perf/2026-09-27-r15-r18.md) for methodology and full numbers).

- **R15** `FileHashService.GetAsync` pre-await `FileInfo.Length`/`LastWriteTimeUtc`: 0.03 ms median, 1996 real files.
  Smaller than R01-R13's already-negligible metadata-I/O band.
- **R16** `ReviewCatalog.EntriesSnapshot()`: 0.24 ms median / 2.78 ms max at 50,000 synthetic entries (25x the
  current F4 fixture), and runs only once per new preload lifetime, not per navigation. Not material at any
  realistic catalog size.
- **R17** `DragDropInputService.Parse` per-path `Exists` checks: 2.88 ms median for an unusually large 50-path
  drop on local disk. NAS/UNC-path latency is unmeasured (no fixture), same open gap as Q-R29.
- **R18** `ReviewMetrics.Snapshot` source-open sort at the documented 4096-entry cap: 0.28 ms median / 11.3 ms max,
  on an on-demand diagnostics-dialog/perf-instrumentation path, never the per-navigation hot path.
