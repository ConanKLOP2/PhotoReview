# R06/R07/R11/R08 — benchmark/cache misc and instance-forward ambiguity

Full code review (2026-09-27), fixed in #194 (`perf/benchmark-cache-misc`):

**R06** — No source change: `PreviewImageService`'s queued-persist backlog (`PersistQueueCapacity`=16 + `PersistWorkerCount`=2 = 18 bitmaps max retained outside the RAM LRU while queued for disk write) measured at ~0.56 GiB worst case (18 x the app's own "largest sane preview" box, 3840x2160x4 bytes, `RamBudgetPolicy.MinimumBudgetBoxWidth/Height`) -- negligible against the 16 GiB preview-cache target and well under the smallest configured budget. No realistic slow-disk-write scenario could be constructed: the persist writer (`PreviewCacheFile.WriteAtomicallyAsync`) is a static method with no injectable slow-writer test seam. Added a regression test pinning the two constants (`PreviewImagePersistQueueBoundTests`) so a future bump to either is a deliberate, reviewed decision. See [perf measurement](../perf/2026-09-27-r06-r07-r11-benchmark-cache-misc.md).

**R07** — Fixed: `PerformanceTestHarness.MeasureParallelAsync` (benchmark tooling only) now acquires each file's concurrency-gate slot in the loop, before creating that file's `Task`, instead of creating one `Task` per selected file up front and having each wait on the gate internally -- a `take` far larger than `workers` no longer pre-creates one thread-pool work item per file. Verified: concurrency is bounded (`PerformanceHarnessConcurrencyTests`, mutation-checked against the old eager-creation code) and the existing benchmark-report tests (order, stats, JSON shape) still pass unchanged.

**R11** — Fixed: `BenchmarkWindow.RunAsync`'s folder-exists check, top-level file listing and stat pass (`EnumerateAndStat`) now run on a background thread instead of synchronously on the dialog's dispatcher before the method's first await; measured 203 ms to enumerate+filter 100,000 top-level entries locally (77 ms for 20,000), which is already a visible dispatcher stall for a large local folder and would be materially worse over the app's supported NAS/network-drive scenarios (see Q-R29). Cancellation is now polled every 256 enumerated entries so Cancel/Close can interrupt an in-progress scan, not just the profile run that used to follow it. The image-count cap, enumeration order and stat-sum semantics are unchanged (`BenchmarkWindowEnumerateAndStatTests`); the folder-missing/no-images/cannot-read-folder status messages and button-lifecycle regression, plus a mid-scan Cancel, are covered by `BenchmarkWindowEnumerationUiTests`.

**R08** — Decided (Option 1, low-risk reclassification): `InstanceForwardClient.SendAsync` now returns `Unknown` instead of `NoInstance` for BOTH ambiguous post-write silent-hangup paths (empty reply, and IOException/UnauthorizedAccessException) once the request write itself succeeded (`written`) -- matching the pattern the post-write-timeout case already used. The client fundamentally cannot tell "nobody home" apart from "owner accepted, started handling, then dropped the connection" without a wire-protocol accept-ack (the rejected, more invasive Option 2); `SecondInstanceHandoff.TryForwardAsync` (Q-R12) already treats `Unknown` the same as `Delivered` ("very likely took over, exit"), so this is the safer default: it risks occasionally not opening a path that truly had no owner, never a duplicate window for one the owner already handled. Both existing hangup tests (`Client_OwnerHangsUpSilentlyAfterWrite_ReportsUnknown`, `Client_OwnerAcceptsThenHangsUpBeforeReplying_ReportsUnknown`) updated and mutation-checked (reverting the fix made both fail as expected).
